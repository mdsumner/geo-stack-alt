# GDAL 3.13 changed bilinear/cubic warping for downsampling factors between 1 and 2

2026-11-10. Found while comparing arm A (pip, rasterio) with arm B (pixi, osgeo.gdal + R).

Upstream tracking: `~/Git/osgeo-upstream/notes/2026-11-10-warp-4sample-threshold.md` (with an offline
repro, LEDGER rows and a PLANS entry). This file is the stack-side view.

## Symptom

The probe job (Copernicus 30 m DEM COG, `/vsicurl/`, warped to a 40 km EPSG:3577 box at 40 m,
bilinear) gave two answers:

| stack | GDAL | min | max | mean |
|---|---|---|---|---|
| pip: rasterio 1.5.2 wheel | 3.12.2 | 73.000 | 1425.759 | 558.9196 |
| apt libgdal-dev + osgeo.gdal | 3.8.4 | 73.000 | 1425.759 | 558.9196 |
| pixi: osgeo.gdal, gdalraster, vapour | 3.13.3 | 72.837 | 1426.728 | 558.9198 |

## Isolation (each in a clean ubuntu:24.04 container, conda-forge GDAL via pixi)

1. **Version, not binding.** `gdal.Warp` alone: 3.10.3 = 3.11.5 = 3.12.4, all differ from 3.13.3.
   99.6% of cells differ; median |diff| 0.32 m, max 10.9 m; 3.13 output is ~4% rougher.
   (`evidence/warp-versions/`)
2. **Resampling kernel, not geometry.** `near` and `average` are bit-identical across 3.12/3.13;
   `bilinear` and `cubic` differ. Source georeferencing (pixel-is-point) is read identically.
   3.13 `bilinear` is bit-identical to 3.12 `bilinear` with `-wo XSCALE=1 -wo YSCALE=1`.
   (`evidence/warp-variants/`)
3. **Scale computed but not applied.** With `CPL_DEBUG=ON`, 3.13 logs
   `dfXScale = 0.588881, dfYScale = 0.746642`, yet every explicit XSCALE/YSCALE (1, 0.589/0.747,
   0.529/0.675) gives bit-identical output in 3.13. In 3.12 each value changes the output.
   (`evidence/warp-debug/`, `evidence/warp-scales/`)
4. **Threshold at 2x.** Offline synthetic repro (`cleanroom/experiments/warp_scope2.py`), same CRS,
   Float32, bilinear: 3.13 applies no anti-aliasing for 10 m -> 12.5/15/17.5 m, and does for
   20/25/40 m. 3.12 anti-aliases all of them. Integer 2x downsampling is unaffected for every data
   type and kernel (`warp_scope.py`). GDAL master (3.14.0dev, 2026-11-03) behaves like 3.13.
   (`evidence/warp-scope*/`)

## Cause

OSGeo/gdal commit `7e18bd36cf` (2026-01-29, released in 3.13.0), "Warper: improve XSCALE/YSALE
computation logic when the target shape is quite different from the source shape". Besides the
new scale computation, it changes when the 4-sample (no anti-aliasing) bilinear/bicubic formula is
used:

```c
// 3.12 alg/gdalwarpkernel.cpp
const int bUse4SamplesFormula = dfXScale >= 0.95 && dfYScale >= 0.95;
// 3.13 / master: CanUse4SamplesFormula()
if (poWK->dfXScale > 0.5 && poWK->dfYScale > 0.5) return true;
```

From the commit message: "Previously we only used the 4-sample formula if not downsampling (with a
margin error of 5%). Increase that tolerance to allow up to a 50% downsampling." The NEWS entry
mentions only the scale computation, not this threshold.

So: **intentional**, upstream, and not specific to any packaging. In 3.13+ there appears to be no
warp option that restores the 3.12 result for factors in (1, 2): XSCALE/YSCALE are ignored on the
4-sample path. (Not yet tested: XSCALE <= 0.5 forces the general kernel, but with a different
kernel width than 3.12 would have used.)

## What it means for the stack argument

- "Identical answers" is a property of **one GDAL**, not of a language or binding. osgeo.gdal,
  gdalraster and vapour agreed to the last digit because they shared one libgdal. rasterio
  agreed with apt GDAL 3.8 because both were pre-3.13.
- The wheel stack hides which GDAL you have. rasterio 1.5.2 ships 3.12.2 and pyogrio 0.13.0 ships
  3.12.4, in the same process. When those wheels move to 3.13, bilinear/cubic warps of this kind
  change silently on `pip install -U`.
- The pixi stack pins the exact libgdal build in `pixi.lock`, and every language in the env sees
  that one build. That is the reproducibility claim to make, with this as the worked example.
- Guideline: record the GDAL version (and resampling) in every output's metadata.

## Open

- Upstream: tracked in osgeo-upstream (see top). Not filed.
- Which result is "right" depends on intent: 3.12 averages more (smoother, less aliasing); 3.13
  is closer to point interpolation (sharper). For a DEM at 1.3-1.75x coarser, 3.13 is arguably
  closer to what most people expect from "bilinear"; for reflectance it adds aliasing.
